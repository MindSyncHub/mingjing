## 一、架构总览

### 1.1 架构原则

1. **插件化**：通用底座 + 流派插件 + 应用工作流，三层可插拔
2. **本体论驱动**：所有知识和推理基于本体论骨架，不是纯向量检索
3. **文档驱动**：先写 spec 再写代码，架构与文档同步演进
4. **框架可替换**：业务逻辑与 Agent 框架解耦，通过薄适配层交互
5. **单端两场景**：同一套知识体系，通过场景配置支持"解读参谋 + 应答准备"两种使用方式
6. **安全优先**：应答准备场景的输出可能被转述给来访者，按"最终可能被来访者读到"的标准做安全审核

### 1.2 三层架构

```
┌─────────────────────────────────────────────────────────┐
│  应用工作流层（Application Workflows）                    │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐       │
│  │报告生成  │ │报告问答  │ │话术助手  │ │个案模拟  │ ...   │
│  │(MVP)    │ │(MVP)    │ │         │ │         │       │
│  └─────────┘ └─────────┘ └─────────┘ └─────────┘       │
├─────────────────────────────────────────────────────────┤
│  流派插件层（Framework Plugins）                         │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐                 │
│  │ 曼陀罗    │ │ 人类图    │ │ 塔罗     │ ...            │
│  │(MVP)     │ │          │ │          │                 │
│  └──────────┘ └──────────┘ └──────────┘                 │
├─────────────────────────────────────────────────────────┤
│  通用底座层（Common Base）                               │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐   │
│  │本体论引擎 │ │知识库引擎 │ │Agent引擎  │ │安全护栏引擎│   │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘   │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐   │
│  │对话管理   │ │档案管理   │ │用户管理   │ │评估系统   │   │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘   │
└─────────────────────────────────────────────────────────┘
```

应用工作流层之上有一层薄的「主 Agent 调度层」作为统一入口，负责任务判别与路由、自主程度分级放行、失败降级与 trace 入口；MVP 阶段任务判别由人在入口显式指定 Agent，自动判别非优先，详见 §2.1。

## 二、应用工作流层

### 2.1 主 Agent 调度层（多智能体入口）

**定位**：应用工作流层的统一入口 + 薄调度层。随 Agent 数量增加（报告生成、报告问答，以及后续个案复盘/督导/预演/陪练等），需要统一入口承接「接什么活、交给谁、怎么兜底」，避免各工作流各自实现护栏与溯源。

**分工原则（主 / 子 / 底座）**：

- 主 Agent：任务判别、路由、自主程度分级放行、失败降级、会话上下文装配、trace 入口
- 子 Agent（各工作流）：领域判断、话术、知识调用、本工作流的异常处理
- 通用底座：安全护栏、知识库、工具白名单、记忆/会话、trace 存储

一句话：**主 Agent 管「接什么活、交给谁、怎么兜底」，子 Agent 管「这个活怎么干」；主 Agent 不做领域判断，子 Agent 不碰路由和安全。**

**设计选型（A/B/B）**：

- 主 Agent 形态：薄路由 / 门卫（不做规划、不迭代），非厚编排器
- 共享能力归属：全部沉淀到通用底座，主 Agent 只做入口
- 会话 / 记忆归属：底座统一「会话 / 记忆层」，子 Agent 只声明需要的上下文

**MVP 口径**：

- 任务判别由「人在入口显式指定 Agent」承担，主 Agent 的自动意图判别非 MVP 优先（使用者直接选择报告生成 / 报告问答即可）
- 主 Agent 在 MVP 阶段落地为「统一入口 + 底座连接 + 兜底」，自动路由能力随 Agent 数量增加再补

### 2.2 MVP 核心工作流

#### WF-01：曼陀罗绘画解读报告生成

- **优先级**：P0（MVP 双核心之一）
- **使用者**：曼陀罗疗愈师
- **输入**：曼陀罗画作 + 用户基本信息 + 主题（可选）
- **输出**：结构化解读报告（PDF / 网页）
- **核心能力**：
  - 画面特征提取（颜色、形状、位置、三圈结构）
  - 信号→状态映射（基于曼陀罗流派映射规则）
  - 本体论关联推理（因果链、五行乘侮、跨议题关联）
  - 报告结构化生成（按报告模板组织内容）
- **详细设计**：见 specs/WF-REPORT-GEN.md

#### WF-02：报告问答（疗愈师端两场景）

- **优先级**：P0（MVP 双核心之一）
- **使用者**：疗愈师（单端，问答助手不直接面对来访者）
- **输入**：报告 ID + 疗愈师问题（+ 可选场景标识：advisor / reply_prep）
- **输出**：回答 + 来源标注 + 边界提示（+ 应答准备场景的口径提醒）
- **两场景设计**：

| 维度 | 场景一：解读参谋 | 场景二：应答准备 |
|---|---|---|
| 触发时机 | 生成报告后、交付前 | 交付后，来访者提问时 |
| 回答深度 | 深（根因+核心+表现） | 中（核心+表现，避免过度解读） |
| 语言风格 | 专业精准 | 专业 + 可转述 |
| 知识库范围 | 全部知识单元 | 全部知识单元 |
| 安全等级 | L1 基础 | L2 标准（输出可能被转述给来访者） |
| 免责声明 | 报告末尾即可 | 敏感回答附口径提醒 |

- **演进方向**：问答能力深化（来源标注、多报告关联）与疗愈师工作流（个案管理、实时话术辅助）；**不做 to C 疗愈对话**

- **详细设计**：见 specs/WF-REPORT-QA.md

### 2.3 后续扩展工作流

- WF-03：AI 话术助手（MVP 后扩展）
- WF-04：个案模拟练习（MVP 后扩展）
- WF-05：疗愈方案生成
- WF-06：内容流水线（获客素材）
- WF-07：课程开发辅助

## 三、流派插件层

### 3.1 流派目录结构

每个流派一个目录：

```
schools/mandala/
├── manifest.json        ← 流派清单（名称、版本、作者、依赖）
├── framework/           ← 解释框架定义（符号系统 + 映射规则）
│   ├── symbols.md       ← 符号定义（颜色、形状、位置等）
│   └── mapping_rules.md ← 符号→状态映射规则
├── knowledge/           ← 流派专属知识内容
│   ├── report_language/ ← 报告表达风格与话术
│   └── intervention/    ← 流派专属疗愈方法
├── prompts/             ← 流派专属提示词模板
└── tests/               ← 流派测试用例
```

### 3.2 插件接口规范

流派插件与通用底座的接口：

- **符号注册**：插件向本体论引擎注册自己的符号系统
- **映射规则注册**：插件向知识库引擎注册符号→状态映射规则
- **提示词注入**：插件向 Agent 引擎注入流派风格的提示词模板
- **知识内容挂载**：插件知识内容挂载到知识库对应层级

### 3.3 MVP 插件：曼陀罗

- **状态**：开发中
- **核心符号系统**：颜色、形状、位置、三圈结构、组合模式
- **解释框架**：五行体系 + 三才九宫
- **报告风格**：东方能量描述 + 心理学对应，双轨表达

## 四、通用底座层

### 4.1 本体论引擎（Ontology Engine）

**职责**：管理本体论数据，提供状态查询、关系推理、跨流派映射等能力。

**核心能力**：
- 状态 CRUD 与层级管理
- 关系推理（leads_to、correlates_with、五行生克乘侮等）
- 流派概念映射（不同流派术语 → 统一状态 ID）
- 状态属性查询（五行属性、心理学对应、层级等）

**设计要点**：
- 本体论数据与业务逻辑解耦
- 支持动态新增状态和关系
- 提供统一的状态 ID 体系（S-NNN）

### 4.2 知识库引擎（Knowledge Base Engine）

**职责**：管理结构化知识库，提供检索、推理、生成支撑。

**核心能力**：
- 知识单元管理（按五层体系组织）
- 多路召回（结构化 + 向量 + 关键词）
- 场景适配（解读参谋/应答准备的检索策略切换）
- 知识状态分级（ai_draft → source_supported → case_verified → reviewed）

**设计要点**：
- 本体论驱动的结构化 RAG，不是纯向量检索
- 知识单元含"通俗解释"字段：报告与应答场景共用一份知识、两种表达深度（单版本口径）
- 详细设计见 KNOWLEDGE-BASE.md

### 4.3 Agent 引擎（Agent Engine）

**职责**：管理 Agent 生命周期，提供对话、工具调用、工作流编排能力。

**技术选型**：
- **MVP 阶段**：自研薄编排（FastAPI 路由 + 固定编排 LLM 调用 + 规则代码，无第三方 Agent 框架）
  - 与两份 wf spec 红线一致（固定编排 + 规则代码；框架须经维护者确认后进白名单）
  - 黑盒程度为零，调试与审计成本最低
  - MVP 双工作流控制流均可预设，无框架能力缺口
- **升级路径**：出现 3+ Agent 稳定协同、状态持久化需求、企业级安全需求时，再评估引入编排框架（须经维护者确认后进白名单）

**核心 Agent 角色**：
- 主 Agent（调度/入口，薄路由，详见 §2.1）
- 报告生成 Agent（疗愈师版）
- 问答 Agent（advisor / reply_prep 两场景配置）

> 安全护栏与评估属于通用底座（§4.4 / §4.7），不作为应用子 Agent；子 Agent 只对应应用工作流。

**设计要点**：
- 业务逻辑不绑定具体 Agent 框架（框架可替换原则，AGENTS §5.3）
- Agent 角色与工作流一一对应
- 工具调用统一通过底座工具层

### 4.4 安全护栏引擎（Safety Guard Engine）

**职责**：确保系统输出安全、合规、不越界。

**安全分级**：
- **L1 基础**（解读参谋场景）：过滤违法违规内容
- **L2 标准**（应答准备场景）：不做诊断、不做承诺、不绝对化、危机干预——输出可能被转述给来访者，按"最终可能被来访者读到"的标准审核

**核心能力**：
- 输入安全检测（危机信号、严重心理问题、医学/法律/财务问题）
- 输出安全审核（诊断类、承诺类、绝对化、超范围、评判性）
- 免责声明管理（报告末尾、敏感话题口径提醒）
- 危机干预话术触发

**设计要点**：
- 安全护栏与知识库联动（知识单元自带风险标签）
- 四级内容分级体系（安全/提醒/谨慎/禁止）
- 详细设计见 KNOWLEDGE-BASE.md 安全护栏章节

### 4.5 对话管理模块

**职责**：管理多轮对话状态、上下文、历史记录。

**核心能力**：
- 会话创建与管理
- 上下文窗口管理（报告锚定 + 分层摘要）
- 对话历史检索
- 场景切换（解读参谋/应答准备）

### 4.6 档案管理模块

**职责**：管理个案档案、报告记录、用户数据。

**核心能力**：
- 报告存储与检索
- 个案档案结构化管理
- 用户画像与历史追踪
- 数据隐私与权限控制

### 4.7 评估系统模块

**职责**：评估系统输出质量，驱动迭代优化。

**核心能力**：
- 黄金测试集管理
- 多维度评估（检索准确率、生成质量、安全性等）
- Bad Case 收集与分析
- 版本对比评估

## 六、关键设计决策

### 6.1 为什么用本体论驱动的结构化 RAG？

- 普通向量 RAG 只能"找相关文字"，不能保证推理链条正确
- 本体论驱动的 RAG 按知识单元组织，每个单元有明确的类型、关系和属性
- 推理过程可追溯：从符号 → 状态 → 关系 → 结论，每一步都有依据
- 场景适配更简单：同一套知识单元，按场景切换表达深度，不需要两套知识

### 6.2 为什么应答准备场景要做标准级安全护栏？

- 应答准备的输出会被疗愈师消化后转述给来访者——审核标准是"最终可能被来访者读到"
- 疗愈领域涉及心理、情绪等敏感话题，输出不当可能造成伤害
- 安全护栏不是限制能力，而是保护来访者、疗愈师和产品
- MVP 阶段先做 L2 标准级，验证后再逐步放开

### 6.3 为什么主 Agent 调度层选「薄路由」而非「厚编排」？

- 当前及近期 Agent 都是「人指定任务」的同步/异步工作流，不存在需要主 Agent 自主拆解、迭代规划的强需求
- 厚编排器（主 Agent 规划 + 迭代）黑盒度高、难审计、延迟大，与「框架可替换、可追溯」原则冲突
- 能力沉淀在通用底座（护栏/知识库/记忆），主 Agent 只做入口和兜底，随 Agent 数量增加再补自动意图判别

## 七、全局工程规约（跨工作流统一口径）

### 7.1 LLM 调用重试与降级（WF-REPORT-GEN / WF-REPORT-QA 共用）

- 每次 LLM 调用最多重试 2 次（共 3 次尝试），指数退避
- **核心步骤失败**（报告生成的视觉解析/五行/报告生成；问答的分类/检索生成）→ 整轮终止报错，**不留半成品**
- **可缺步骤失败** → 跳过该步并留痕
- 输出 JSON 解析失败 → 原样重跑，仍失败按核心步骤失败处理
