## 一、验收总原则

### 1.1 三层验收体系

参考 Agent 架构三层世界观，验收也分三层：


| 层级      | 验收对象      | 回答的问题 | 验收方式            |
| ------- | --------- | ----- | --------------- |
| **设计层** | 产品设计与业务价值 | 做对了吗？ | 需求评审 + 用户验证（疗愈师） |
| **控制层** | 质量控制与安全护栏 | 稳得住吗？ | 自动化评估 + 人工抽检    |
| **工程层** | 功能实现与性能   | 跑得通吗？ | 功能测试 + 性能测试     |


### 1.2 评估面 vs 客户面


| 分类            | 内容                      | 负责方               |
| ------------- | ----------------------- | ----------------- |
| **评估面**（技术质量） | 系统质量标准、评估集维护、回归纪律、安全护栏  | 开发/产品团队           |
| **客户面**（业务价值） | 解读专业性、报告可用性、问答满意度、交付体验 | 目标用户评审（疗愈师）+ 来访者反馈（经疗愈师访谈间接收集） |


> MVP 阶段用户为项目团队自身 + 合作疗愈师，客户面验收由团队内部模拟 + 疗愈师评审结合；来访者侧反馈通过疗愈师访谈间接收集（后无来访者端产品界面）。

### 1.3 单端验收原则（D-106 本地形态）

MVP 为**单用户本地工具**（D-106）：无多租户、无前端，CLI/本地 API 交互，报告与问答产物落盘为本地文件。验收围绕疗愈师工作流的三个环节进行，所有功能项按本地形态判定：

- **报告生成**：专业深度、效率、证据链
- **问答助手**：解读参谋场景的深度、应答准备场景的可用性
- **PDF 交付**：导出质量、可读性（来访者读得懂的报告才算交付成功）

### 1.4 通过标准

MVP 验收通过需同时满足：

- 工程层：所有 P0 功能测试通过率 100%
- 控制层：核心质量指标达到 MVP 目标值（两场景分别达标）
- 设计层：目标用户（疗愈师）主观评价达到"可用"门槛

## 三、控制层验收（质量 + 安全）

### 3.1 报告质量评估

#### 3.1.1 评估集构建

**基准测试集（Benchmark Set）**：选取 10 幅具有代表性的曼陀罗绘画作为标准测试集


| 类别   | 数量  | 说明              |
| ---- | --- | --------------- |
| 典型案例 | 4 幅 | 结构清晰、特征明显的常规案例  |
| 边界案例 | 3 幅 | 结构不典型、特征模糊的困难案例 |
| 极端案例 | 3 幅 | 单色、极简、极复杂等极端情况  |


每幅测试画配套：

- 人工标注的标准答案（五行分布、核心议题、主要状态）
- 资深疗愈师撰写的参考报告（同时作为可读性基准：术语友好、文内解释， 单版本口径）

#### 3.1.2 质量维度与指标


| 维度         | 指标        | 计算方式                 | MVP 目标     |
| ---------- | --------- | -------------------- | ---------- |
| **完整性**    | 章节完整率     | 实际生成章节数 / 标准章节数      | 100%（8章全有） |
| **一致性**    | 核心结论一致率   | 同图多次生成，核心结论相同的比例     | > 80%      |
| **准确度**    | 五行判断准确率   | AI 判断的五行分布与人工标注的吻合度  | > 70%      |
| **准确度**    | 议题定位准确率   | 核心议题宫位与人工标注的吻合度      | > 70%      |
| **证据链**    | 结论有证据比例   | 主要结论中，有画面证据支撑的比例     | 100%       |
| **深度**     | 根因层触及率    | 报告中触及根因层状态的比例        | > 60%      |
| **可操作性**   | 建议具体度评分   | 每条调理建议的具体可执行程度（1-5分） | ≥ 3.5 分    |
| **安全性**    | 越界内容数     | 违反安全护栏的内容条数          | 0          |


#### 3.1.3 评估方法


| 方法         | 适用维度              | 说明                     |
| ---------- | ----------------- | ---------------------- |
| **自动化评估**  | 完整性、一致性、安全性       | 脚本自动检查章节结构、关键词匹配、敏感词检测 |
| **半自动化评估** | 准确度、证据链           | AI 辅助对比 + 人工复核         |
| **人工评估**   | 深度、可操作性、专业度 | 疗愈师盲评打分                |

#### 疗愈师端


| 指标           | 问题                        | MVP 目标           |
| ------------ | ------------------------- | ---------------- |
| **报告采纳率**    | "这份报告你觉得可用吗？"（可用/需大改/不可用） | > 70% 选"可用或只需微调" |

#### 来访者侧（间接收集）

无来访者端产品界面，不设直接量化指标。通过疗愈师访谈收集：
- 来访者读完 PDF 报告后的反应（读懂了哪些部分、卡在哪里）
- 来访者提问的典型类型（反哺应答准备场景的测试集）
- 报告是否促成来访者继续与疗愈师沟通

### 4.3 MVP 通过的用户标准

**疗愈师端（全部满足， 口径）：**

1. 报告采纳率 > 70%（M-060）
2. 问答满意度 ≥ 3.5 分（M-064）
3. 至少 2/3 的测试疗愈师表示"愿意继续使用"
4. 应答准备可用性 ≥ 70%
5. PDF 报告经 2 名以上非专业读者试读，无"完全看不懂"反馈

## 五、验收流程

### 5.1 验收阶段划分

```
开发完成
    ↓
第一阶段：工程层验收（功能 + 性能）
    ↓ 全部通过
第二阶段：控制层验收（质量 + 安全）
    ↓ 核心指标两场景分别达标
第三阶段：设计层验收（UAT 用户测试 · 疗愈师）
    ↓ 测试疗愈师全部通过
MVP 验收通过
```

### 5.2 回归测试纪律

- 每次重大改动后，必须跑完整基准测试集
- 核心指标不得低于上一版本（退化即失败）
- 新增功能必须补充对应的测试用例
- 评估集随项目迭代持续扩充（每月至少新增 2 个测试案例）
- 两场景分别回归，一个场景改动不影响另一个场景的质量

### 5.3 验收记录

每次验收产出：

- 验收报告（各维度得分、通过/不通过）
- 问题清单（未通过项、严重程度、修复建议）
- 改进建议（非阻断性的优化方向）
- 两场景分别统计
