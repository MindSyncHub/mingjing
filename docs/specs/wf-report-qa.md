# 第一层：设计层（是什么、不是什么）

## 1.1 定位与两场景

报告问答是疗愈师端的报告深度理解助手，服务两个场景：

**场景一：解读参谋（advisor）**——报告生成后、交付前，疗愈师把自己的疑问问透：某个状态的深层原因、结论怎么从画面推出来、两幅报告哪里矛盾、有哪些疗愈方向。先想透，再面对来访者。

**场景二：应答准备（reply_prep）**——报告交付来访者后，来访者提问，疗愈师拿不准或想组织得更专业时，借助助手准备回应素材，消化后用自己的话回应。**助手不直接面对来访者**。

| 维度 | 解读参谋 | 应答准备 |
|---|---|---|
| 触发时机 | 生成报告后、交付前 | 交付后，来访者提问时 |
| 核心目标 | 帮疗愈师想透报告 | 帮疗愈师组织可转述的回应 |
| 语言风格 | 专业、精准、有深度 | 专业 + 可转述（通俗、疗愈师消化后转达） |
| 回答深度 | 深（根因层 + 核心层 + 表现层） | 中（核心层 + 表现层，避免过度解读） |
| 回答策略 | 多视角、深分析、重逻辑 | 给可能性不给定论 + 附"回应来访者时的边界口径"提醒 |
| 安全等级 | L1 基础 | L2 标准（输出可能被转述给来访者） |
| 轮次建议 | 不限 | ≤ 15 轮 |

## 1.2 输入契约

| 参数 | 必填 | 说明 |
|---|---|---|
| `report_id` | 是 | 关联报告 ID；无效则终止并报错（见 2.4） |
| `user_question` | 是 | 疗愈师问题（应答准备场景可能是转述的来访者原话） |
| `scenario` | 否 | `advisor` / `reply_prep`，缺省 `advisor` |
| `conversation_history` | 否 | 多轮对话历史 |
| `client_info` / `therapist_notes` | 否 | 来访者基本信息 / 疗愈师备注 |

**`report_id` 加载的报告上下文（三层）**：
1. **报告正文**（必注入）：报告 Markdown 全文
2. **三级链路确定性产物**（必注入）：报告元数据中的结构化结论——五行分布、核心失衡模式、核心状态（含层级/证据链/置信度）、核心议题。这是"报告为什么这样写"的确定性依据，回答依据**以本层为准、正文为辅**；正文与产物冲突时以产物为准并指出矛盾
3. **解读 trace**（按需注入）：WF-REPORT-GEN 各步中间产物（Step 1 信号 / Step 2 失衡 / Step 3 状态 / Step 4 议题，trace_record 落盘）；细节追问、深度探讨、视角切换、跨议题关联类问题必引，方案细化类可选（注入策略与预算见 §3.5）

## 1.3 输出契约

**回答组成**（每轮必含前两项）：
1. **回答文本**
2. **来源标注**：报告章节 + 知识单元 + 涉及的链路产物（如"Step 2 失衡模式：火乘金"）
3. **边界提示**（仅超范围内容时）：标注"这是延伸探讨，不是报告结论"
4. **回应提示**（仅应答准备场景）：给可能性不给定论的口径提醒
5. **口径提醒**（仅敏感话题时）："能量层面的参考，不是诊断；必要时寻求专业帮助"

**元数据**：`qa_id` / `report_id` / `scenario` / `question_type` / `confidence` / `safety_level`

## 1.4 问题分类与场景适配

| 类型 | 说明 | 示例 | 场景适配 |
|---|---|---|---|
| 细节追问 | 报告中某结论/术语的解释，或指认画面某区域 | "配得感不足是什么意思？""中间这圈的黄色代表什么？" | 两场景 |
| 深度探讨 | 挖掘状态的原因、影响、关联 | "为什么我会有配得感不足？" | 解读参谋为主；应答准备适度 |
| 视角切换 | 换框架看同一问题 | "从心理学角度怎么解释？" | 两场景 |
| 方案细化 | 调理建议的具体操作 | "这个冥想怎么做？" | 两场景；应答准备给可转述版本 |
| 跨议题关联 | 延伸到相关议题 | "财富问题跟亲密关系有关吗？" | 两场景；给可能性不给定论 |
| 应答组织 | 转述来访者提问 → 回应素材 | "我的来访者问：水多火灭是什么意思？" | 应答准备特有 |

> **画面指认类输入的归类**：指着画面某区域提问（"外圈这圈蓝色""中间这圈的黄"）归入**细节追问**，不另设类型。检索时除报告章节外**必须注入 Step 1 画面信号层**；"哪一圈"按定稿图标记参数（圆心、R、r1/r2）对齐，不依赖模型目测圈界。

## 1.5 绝对不做（Hard Boundaries）

1. **不直接面对来访者**：所有输出以疗愈师为读者；无任何来访者可用入口
2. **不做诊断/承诺/绝对化**：只用"倾向""可能""可能有帮助"
3. **不做报告范围外的深度疗愈话题**：超出报告的问题标注"延伸探讨"，不展开（MVP）
4. **不做 to C AI 疗愈对话 / 自助形态**（无 L3）
5. **MVP 不做**（完整版规划见 prd.md 演进方向）：多报告关联问答、来源标注增强、推理链展示、个案管理集成

# 第二层：控制层（状态流转写死）

## 2.1 总体状态机（每一轮问答）

```
[接收提问] --report_id 无效--> 终止报错
    ↓
[Step A 输入安全检测] --命中--> 异常路径（2.4）：危机话术 / 建议就医 / 拒绝，本轮结束
    ↓ 正常
[Step B 问题分类] → 六类之一
    ↓
[Step C 检索-生成]（策略按类型写死，见 2.2）
    ↓
[Step D 输出安全审核] --不通过--> 改写重生成（最多 2 次）；仍不过 → 降级输出
    ↓ 通过
[Step E 组装输出] 回答 + 来源标注 + 边界/回应/口径提示
    ↓
多轮循环（回[接收提问]；轮次控制见 2.3）
```

## 2.2 主流程步骤（每步：任务 / 规则 / 失败处理）

**Step A 输入安全检测（规则执行，见 2.4 表）**：检测危机信号、严重心理问题、医学/法律/财务问题、恶意提问；命中即按预设话术处理，不进入生成。

**Step B 问题分类**：LLM 将问题归入六类之一，输出 `question_type`；无法归入时按"细节追问"处理并降低置信度。

**Step C 检索-生成**（检索顺序固定，按类型写死）：

| 类型 | 检索 | 工具序列（按序执行，前序输出作后序输入） | 生成要点 |
|---|---|---|---|
| 细节追问 | 关键词定位报告章节 → 关联 state_id → 检索状态讲解 | report_search → state_query → knowledge_retrieve | 定义 + 心理学对应 + 能量分析 + 本议题语境 |
| 深度探讨 | state_id → 因果链（状态.md §三）→ 根因层状态 | state_query → reason_chain → knowledge_retrieve | 解读参谋：从根因层逐层展开；应答准备：从表现层切入、不做深度创伤解读 |
| 视角切换 | 确定目标视角 → 同一 state_id 换解释框架 | state_query → knowledge_retrieve | 对比两视角差异；应答准备附"大白话转述"建议 |
| 方案细化 | 定位疗愈动作 → 检索操作步骤/注意事项 | intervention_query → knowledge_retrieve | 完整步骤 + 原理 + 变体；应答准备附简化转述版 |
| 跨议题关联 | 主议题 → 共享状态/五行生克找路径 → 检索佐证 | five_elements_reason → state_query → knowledge_retrieve | 关联路径 + 共享分析 + 调理建议；给可能性不给定论 |
| 应答组织 | 识别来访者真实意图（术语不懂/担心严重/求建议） | report_search → state_query → knowledge_retrieve | 回应素材 = 核心答案 + 报告依据 + 边界口径 + 回应提示 |

**工具序列规则**：序列按序执行，前序输出作为后序输入；**序列之外不得调用其他工具**（§3.1 红线 3 的具体化）；画面指认类细节追问先按标记参数对齐圈层、取该圈信号记录，再执行序列。

**Step D 输出安全审核（规则执行）**：逐条检查 2.4 输出审核表；命中即按该条规则改写。

**Step E 组装输出**：按 1.3 输出契约组装，缺来源标注视为不完整，禁止输出。

## 2.3 多轮控制

- **报告锚定**：每轮注入报告三层上下文（见 1.2）；回答必须引用报告具体段落或结论，"为什么这样解读"类问题必须引用链路产物
- **轮次**：硬限制——应答准备 15 轮、解读参谋 30 轮；到限正常应答并提示开启新会话
- **上下文溢出**：按 knowledge-base.md §7.3 处理（滚动摘要，报告内容始终保留、对话历史可摘要、核心状态常驻）
- **轮次留痕**：每轮问答（含 Step A 护栏拒绝与 Step D 降级话术）落盘 `runs/<report_id>/qa/turn-NNNN.json`，一问一文件，字段含 scenario、question、question_type、answer、sources、审核结论、边界/口径提示、时间戳；护栏拒绝与降级话术同等待遇写成正式回答——历史里可见，避免重复踩同一红线。本工作流只写 `qa/` 子目录，报告产物只读不写

## 2.4 异常路径总表（每一条都是预设规则）

| 异常 | 检测点 | 处理规则 |
|---|---|---|
| 危机信号（自伤/自杀/严重自残） | Step A | 触发危机干预话术 + 求助资源；若为疗愈师转述的来访者原话，提示疗愈师注意个案风险 + 转介话术参考；本轮不做常规回答 |
| 严重心理问题（重度抑郁、精神病性症状） | Step A | 建议就医，不做解读 |
| 医学问题（诊断、用药） | Step A | 建议咨询医生 |
| 法律/财务问题 | Step A | 建议咨询专业人士 |
| 恶意提问 | Step A | 礼貌拒绝，本轮结束 |
| report_id 无效 | 输入校验 | 终止报错，不进入流程 |
| 问题与报告无关 | Step B/C | 可答但标注"延伸探讨，不是报告结论"；不展开深度疗愈 |
| LLM 调用失败 | 任一步骤 | 工程容错 Retry（全局口径见 architecture.md §7.1） |
| 输出审核不通过 | Step D | 按审核规则改写重生成，最多 2 次；仍不通过 → 输出降级回复（"该问题暂无法安全回答，建议参考报告相关章节"）并留痕 |

**输出审核规则表（Step D 执行）**：

| 检查内容 | 命中处理 |
|---|---|
| 诊断类（"你有 XX 病/症"） | 改为可能性描述 |
| 承诺类（"一定会好""肯定有效"） | 改为"可能有帮助" |
| 绝对化（"所有""永远""必须"） | 改为"可能""往往" |
| 超范围（超出报告范围） | 标注"延伸探讨" |
| 评判性（"你不对""你应该"） | 改为接纳性表达 |
| 重大决策引导（分手、辞职等） | 删除引导，保持中立 |

## 2.5 回答后操作（每轮输出后的显式操作）

每轮 Step E 输出后，疗愈师可执行三种操作。MVP 不做中断式介入——Agent 每轮之间天然是人工间隙，操作即介入：

| 操作 | 做法 | 复用路径 |
|---|---|---|
| 再生成一版 | 对同一问题重跑生成，可附补充要求（如"更通俗""更简短"） | Step C→D→E；分类结果沿用，不重跑 Step B |
| 指错重分类 | 疗愈师指出正确问题类型（"这不是细节追问，是深度探讨"） | 人工指定类型覆盖 Step B 结果，重走 C→D→E，留痕记录人工修正 |
| 采纳 / 关闭 | 结束本轮，问答历史保留可回溯 | 无系统动作 |

- 再生成与指错重分类不限次数，均计入场景轮次上限
- 每次操作（含人工覆盖的分类）写入对应轮次落盘文件（见 2.3 轮次留痕）

## 2.6 问答历史回读接口

落盘的轮次文件提供只读查询接口，供前端渲染问答历史（如"回答后操作"的上下文展示）：

| 项 | 约定 |
|---|---|
| 接口 | `GET /report-qa/turns?report_id=<id>` |
| 返回 | 按轮次升序的 turn 数组，元素 = 落盘文件全文（turn/timestamp/scenario/question/question_type/answer/sources/audit 等） |
| 异常 | report_id 无效或目录无 qa/ 子目录时返回空数组，不报错 |
| 边界 | 只读 `qa/` 子目录，不触碰报告产物；不删改任何 turn 文件 |

# 第三层：工程层（用什么、不要什么）

## 3.1 技术红线（不要什么）

1. **不引入重量级 Agent 框架**：固定编排 LLM 调用 + 规则代码；框架须经维护者确认后加入白名单
2. **不提供任何来访者侧入口**：无 to C 界面、无开放 API，只有疗愈师工作台的调用入口（单一入口）
3. **不自主扩充工具**：工具仅 3.4 清单中的 6 个，调用顺序按问题类型固定
4. **目录结构固定**：代码目录结构由 architecture.md 定义，不得自行发明

## 3.2 规则与 LLM 的分工

- **规则（可靠性）**：Step A 输入安全检测、Step D 输出安全审核——检测与改写规则全部预设，不依赖模型自觉
- **LLM（决策权）**：问题分类、检索内容选择、回答生成——按 2.2 写死的策略执行
- **工具执行分工**：工具由程序执行（纯函数，输入确定输出确定），LLM 只决定调用参数（检索词、state_id 等），不生成执行代码、不接触文件系统

## 3.3 Agent 角色（MVP）

| 角色 | 职责 |
|---|---|
| 问答 Agent | 按场景配置（advisor / reply_prep）执行 Step B-E |
| 安全护栏 | Step A + Step D 规则执行（代码组件，非独立 Agent） |

> MVP 为纯规则组件，不加 LLM 软审层；规则漏检率由 eval-suite 跑批数据裁决，漏检率高再评估加层。

## 3.4 工具清单（6 个，不扩充）

| 工具 | 功能 |
|---|---|
| report_search | 报告内容检索 |
| state_query | 本体论状态查询 |
| knowledge_retrieve | 知识库检索（全部知识单元） |
| reason_chain | 因果链推理 |
| five_elements_reason | 五行推理 |
| intervention_query | 疗愈方案查询 |

> 调用顺序按问题类型固定，见 2.2 Step C"工具序列"列；6 个工具之外的调用一律禁止。

**接口契约（输入由 LLM 决定，执行与返回由程序负责）**：

| 工具 | 输入 | 返回 | 数据源 |
|---|---|---|---|
| report_search | 检索词（关键词/短语） | 命中的报告段落原文 + 章节锚点 | `runs/<report_id>/report.md` |
| state_query | state_id（问题中的状态名由程序归一化到 S-NNN） | 状态条目：层级、证据链、置信度、讲解 | `runs/<report_id>/context.json` 三级链路产物 + 本体/语义层/状态.md |
| knowledge_retrieve | 检索词 / 知识单元类型过滤 | 命中的知识单元原文 + 规则 ID | `knowledge/healing/`（进 RAG 的知识单元） |
| reason_chain | state_id 或 claim_id | 该结论的推导链：信号 → 失衡 → 状态 → 议题各级证据 | `runs/<report_id>/` 解读 trace（observations.json / hypotheses.json / analysis.md，只读） |
| five_elements_reason | 两个元素（颜色/形状/宫位） | 生克关系判定 + 结构化依据 | 五行解读 生克规则 + 视觉信号映射 形状五行 |
| intervention_query | 议题 ID 或 state_id | 方案条目：动作、步骤、注意事项 | `knowledge/healing/` 方案层（L4） |

> 每个工具只返回命中的最小必要内容，不做全量注入（与 §3.5 trace 注入策略同一口径）；trace 文件名与 Step 1-4 产物的对应关系在实现时以 runs/ 落盘实际为准。

## 3.5 上下文与知识库

- **报告生命周期与挂载口径**：报告不设自动过期或自动删除，生成后长期存档，仅用户主动删除。"当前报告"由打开行为决定，与新旧无关——问答挂载对象永远是用户选定的那份报告，无论是刚生成的还是往期存档（单次解读事后复盘、个案旧档重查均按此覆盖）
- **三层记忆**：短期 = 当前对话历史（上下文窗口）；中期 = 报告全文 + 摘要 + **定稿图与标记参数**（结构化存储；画面指认类问题依赖标记参数对齐圈层，见 1.4）；长期 = 个案档案、历史问答记录（向量库 + 结构化索引，归疗愈师所有）
- **trace 注入策略**：按问题类型按需注入（细节追问只带对应章节的链路产物，深度探讨带因果链路径），不全量注入；报告上下文（全文 + 摘要 + 相关链路产物）≤ 上下文窗口 40%，跑批后调整
- **链路产物来源**：三级链路产物与解读 trace 由 WF-REPORT-GEN 的 trace_record 落盘，本工作流只读不写
- **知识库层级**：L1 本体层（状态/关系）→ L2 流派层（曼陀罗符号）→ L3 议题层 → L4 方案层 → L5 应用层（问答策略、话术模板）

# 第四层：验收层（怎么算完成）

## 4.1 验收指标（口径唯一源：ACCEPTANCE §6.1 指标字典 M-NNN；分值统一 1-5 分制）

**通用指标**

| 指标 | 目标 |
|---|---|
| 锚定报告 | >90% 的回答有报告依据 |
| 相关性 | >85% 的回答与问题直接相关 |
| 准确性 | >90% 事实性内容准确 |
| 一致性 | >80% 与报告结论一致、不矛盾 |
| 安全越界 | 0 条严重越界 |
| 边界清晰 | 100% 超范围内容有标注 |

**解读参谋专属**：专业深度 ≥ 4.0（M-030）｜逻辑性 ≥ 4.0（M-031）｜多视角 ≥ 3 个（M-032）｜可操作性 ≥ 3.5（M-033）

**应答准备专属**：可转述性 ≥ 4.0（M-040）｜不过度解读 = 0 条无依据深层结论｜边界口径 = 100% 敏感回答附提醒｜不评判 = 100%

## 4.2 验收用例（先给用例，再写实现）

1. **功能用例**：六类问题各至少 2 例，两场景均跑通；`scenario` 缺省按 advisor 处理
2. **危机用例**：输入含自伤/自杀信号（含疗愈师转述来访者原话的情形）→ 必须触发危机话术与个案风险提醒，不输出常规回答
3. **输入拦截用例**：医学/法律/恶意提问 → 按 2.4 规则处理
4. **输出审核用例**：构造含诊断/承诺/绝对化/评判/决策引导的回答 → 全部被改写
5. **边界用例**：超范围问题 → 有"延伸探讨"标注，不展开
6. **锚定用例**：抽样回答逐条检查来源标注；无标注视为缺陷
7. **指标测量**：问答满意度 ≥ 3.5（M-064），按 4.1 全表在试点批测量

## 4.3 MVP 验证重点

- 两场景的策略差异是否真实体现（深度 vs 可转述）
- 应答组织类问题（场景二特有）的可用性
- 输入输出安全规则的拦截准确率与误伤率
- 哪些类型的问题最需要人工补充（后续优化方向）
